## Ruling

The existing `apps/interactive-web` is the implementation foundation. Web V1 must evolve it rather than create a replacement application.

## Verified existing surfaces

Repository inspection confirms the application already contains:

- Vite/TypeScript application shell (`index.html`, `package.json`, `tsconfig.json`);
- browser bootstrap and lifecycle tests;
- pointer navigation module and tests;
- Three.js/browser surface module and tests;
- CANON UI presentation module, CSS and tests;
- Dojo Gate contract tests;
- experience shell tests;
- a dedicated CANON content layer under `src/content`;
- curriculum page/projection tests;
- localization and granular localization contracts;
- CANON registry and snapshot contracts;
- Playwright configuration and visual-test surface.

This means Web V1 is not a greenfield implementation.

## Verified CANON/content foundation

`src/content` already exposes tested concepts for:

- curriculum overview/pages;
- experience projection;
- localization;
- CANON registry;
- CANON snapshot.

Therefore the next implementation work should connect these existing contracts into a complete user-facing route graph rather than introduce a second content model.

## Gaps against approved Web V1 spec

### G1 — Information architecture closure

The approved product flow is Entry/Home → Dojo Gate → semantic navigation → TAI/JI/FU knowledge spaces → training/interactive experiences. Existing modules prove pieces of this flow, but the repository still needs one explicit, tested canonical route graph tying the complete journey together.

### G2 — User-facing surface closure

Existing CANON projection/content contracts need to be proven as reachable from the browser experience through semantic navigation, not only as isolated modules/tests.

### G3 — Progressive-enhancement closure

Three.js/pointer systems exist, but Web V1 requires an explicit contract that semantic navigation and content remain available when interactive rendering is absent or reduced.

### G4 — Accessibility/responsive closure

The spec requires semantic HTML, responsive behavior and accessibility. Existing tests provide partial evidence; Web V1 needs route-level evidence for keyboard/semantic fallback and reduced-motion/non-WebGL paths.

### G5 — Browser evidence closure

Playwright/visual infrastructure exists in the repository, but browser evidence must be treated as product evidence when an execution environment is available, not as a GitHub Actions or hosting gate.

## Infrastructure classification

- GitHub Actions: not part of the Web V1 operational architecture.
- Vercel/hosting configuration: optional deployment genealogy/convenience, not Source of Truth and not a development gate.
- WordPress: migration/genealogy source only.
- Vitest/Playwright: product contract tooling retained in code; execution availability does not redefine CANON.

## Task 1 conclusion

Task 1 of the Web V1 implementation plan is complete at repository-evidence level.

The next code task is **Information Architecture**: define the canonical localized route graph using existing CANON/localization contracts, then prove discoverability before changing presentation behavior.
